Keeping typing responsive in a busy remote terminal

Emdash runs coding agents on remote machines over SSH. When several terminals print a lot of output, the keys you type wait behind it, and on a slow link the p95 echo latency was 9 to 11 seconds. This project changes how Emdash sends terminal output so typing stays close to the network delay, and measures what that costs.

The problem

Emdash sends every terminal's output to the desktop app over one SSH connection. A busy terminal fills that connection, and the echo of a key you type queues behind output you are not even looking at. Typing then feels frozen even though the link is fine for other things. Issue #3426 describes the same symptom on a high-latency host.

What the change does

  • A separate lane for typing. Keystrokes and the output of the sessions you are typing into use a second channel, so they do not wait behind bulk updates in Emdash's own queues.
  • Credit for background output. The server sends a terminal's output only while the app is keeping up with it.
  • Back-pressure to the program. When the app falls behind, Emdash pauses reading the terminal, and the program slows down as it would in a plain SSH session.

Architecture

Numbers in this section are the defaults in the code.

Interactive lane

A second Wire channel runs next to the bulk channel on the same SSH connection. Keystrokes, resizes and the output of up to 2 recently typed sessions use it, so they do not wait behind bulk updates in Emdash's own send queues. A session returns to bulk after 30 s idle or when another session displaces it. Both channels still share one SSH connection and one TCP stream, so bytes already in flight can still delay an echo. The adaptive window below limits how many there are.

Adaptive bulk window

The SSH window of the bulk channel is tuned from measured round trips, between 512 KiB and 32 MiB, starting at the stock 2 MiB. If the smoothed round trip rises more than 50 ms above the path's base round trip, the window shrinks by a factor of 0.7. Otherwise it can grow by 1.25. The 50 ms is a target for the controller, not a bound on echo delay.

Credit accounting

For each attached viewer the server adds up the size of every update it sends, and the viewer returns credit as it consumes them. The server sends only while the unacknowledged amount stays inside a window, and it always lets one update through when nothing is in flight. The window adapts to the measured round trip and delivery rate, up to 4 MiB. The size of an update is the length of its JSON text, JSON.stringify(update).length, which both sides count the same way. That is a count of UTF-16 code units, not exact bytes on the wire. Updates over the window wait in a queue of up to 1 MiB.

Back-pressure to the terminal process

When more than 256 KiB is waiting for a viewer, the gate reports pressure. The viewer can also report that its own buffer is full. While either is set, the terminal session calls pause() on its PTY process, which stops Emdash from reading the PTY. The program keeps writing until the kernel's PTY buffer fills, and then its next write blocks. Pressure clears below 128 KiB and reading resumes.

Outbound queue

When the writer pushes back, small control frames keep their order and each live topic gets its own lane. Lanes share the writer by deficit round robin with a 64 KiB quantum. A topic whose oldest queued update is older than 3 s, or that holds more than 16 MiB, drops its backlog and sends a gap, and the viewer resyncs from a snapshot.

When the link is slow

  1. Eight terminals print. Each viewer's credit window fills, so the server queues their output instead of sending it.
  2. Past 256 KiB queued, the gate raises pressure and Emdash stops reading that terminal's PTY.
  3. Once the kernel's PTY buffer is full, the program's next write blocks. The command waits, much as it would over plain SSH.
  4. The bulk window shrinks when round trips rise, so the SSH connection holds less bulk data. Keystrokes and echoes use the lane and wait behind less.
  5. When the app catches up and credit returns, pressure clears and the program continues.
  6. If a viewer returns no credit for 30 s, or a topic's backlog gets too old or too large, that output is dropped and the viewer resyncs from a snapshot.

Trade-offs. Commands with heavy output finish later, because they wait instead of racing ahead and having output discarded. A program that writes to the terminal while doing other work can stall on a paused PTY. Output can still be dropped: the modified runs skipped 0.05 MB per session on the 5 Mbit link, against 0.61 MB for upstream. The design adds coordination state, extra frame types and a larger attach and reconnect surface. It was tuned on recorded traces and may not suit every workload.

Method

Eight background sessions each run one real command at the same time, started together from outside the shaped link. A ninth session receives one typed key every 150 ms, and the echo time is measured. Output goes through each session's terminal, so a paused terminal really blocks its command.

  • Versions: unmodified upstream, upstream with SSH compression, and the modified code.
  • Heavy command: a real type-check with full module tracing, about 3.2 MB of output per command. Light command: a real test run, about 6 KB.
  • Links: tc netem adds 300 ms of delay to the server's outgoing traffic, so the round trip is about 300 ms. The 5 Mbit cap and the 10 s cut (100% loss, starting 8 s after typing begins) apply to the same direction.
  • Runs: 3 repeats, interleaved, each one the only job of mine on the machine. A run counts only if all 8 commands exit 0. All 45 runs counted.
  • Keys without an echo are keys sent but not echoed within the observation window. The window ends when the commands finish, so on the cut link it can end before the link is restored.

macOS storage-management processes averaged about 1.3 CPU cores on the machine in the days around the runs. It is not known whether they were busy during a given run. A stuck listing process ran earlier and was stopped before the three counted repeats. No run was dropped or rerun because of either. Full details: method.md.

Wire-protocol fix: stale topic frames

update, topic-gap and topic-error frames carry only the topic name. If a viewer closes a topic and a new viewer attaches to it while frames for the old attachment are still in flight, the client applies those frames to the new attachment. The client keeps one entry per topic and looks it up by topic alone (connect.ts:136-155).

The fix

The server stamps the attach request id on the three frames as an optional attachId, and returns it in the attach result. The client remembers, per topic, the ids it has left and drops a frame stamped with one of them. That covers its own attach id and, for a shared attachment, the id the server reported. Frames without an id, and frames from a shared attachment, behave as before, so old and new peers still talk to each other, although an old server gets no protection. The change is 69 lines added and 8 removed in protocol.ts, serve.ts and connect.ts.

Regression tests

17 new tests in stale-topic-frames.test.ts run the real serve, connect, LiveLogSource and ReplicaLog over an in-memory transport whose server-to-client direction can be held and released in order. With the fix the wire suite passes (370 tests). On unchanged upstream 12 of the 17 fail, and the rest are guards that pass on both, including one that two connections still share a topic attachment. One test holds a frame stamped with the shared attachment's id, reopens the topic through the second connection and checks the frame is dropped. Two tests cover how long a stale frame can be delayed: one leaves 300 other topics and one reopens the same topic 20 times before the old frame arrives. A first version kept a single set of 256 ids for the whole connection, and the first of those two tests showed that leaving 300 other topics could evict an id while its frame was still in flight. The ids are now kept per topic.

What the frozen log means

The frozen log comes from the test harness, which injects the error through the source. In the desktop app the likely impact is the extra snapshot resync, because no log source in the current code reports a non-retrying error. This is separate from #3426.

Topic sharing is unchanged

Two connections on one transport still share one server attachment. A frame stamped with the other connection's id is delivered, and a detach still removes the shared attachment as before.

The issue is generalaction/emdash#3446 and the pull request is #3447. The issue text is issue/FINAL-ISSUE-BODY.md, the test file is tests/stale-topic-frames.test.ts and the patch is patches/stale-frames-sharing.patch.

Limits

  • One machine, emulated links, a fixed source tree and 3 repeats. Three repeats show large effects, and the completion-time ranges overlap.
  • The heavy command prints 3.2 MB per terminal, less than a large build. The first choice, a larger project, ran out of memory with 8 at once.
  • The typing window on heavy runs is short, about 70 keys.
  • No real coding agent or real remote host was used.
  • Link-cut recovery time could be measured in only one run, so it is not reported.
  • An earlier comparison on replayed recorded output (6 network conditions) pointed the same way. In 3 of those conditions upstream did not finish session setup in the harness, which shows a limit of the harness, not that the app crashes.
  • The wire fix does not give complete stale-frame protection, because nothing in the protocol bounds how long a queued frame can wait. It remembers at most 32 left ids per topic, so a frame delayed past 32 further attach and detach cycles of the same topic on one connection is not recognised. It remembers at most 4096 topics per connection, so after that the ids of the least recently changed topic are evicted and a stale frame for it is not recognised.
  • Reproducing the results on a clean machine, and the relative performance on other hardware, are not verified.
